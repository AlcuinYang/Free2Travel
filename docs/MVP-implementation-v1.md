# LetsGoTravel 第一版实施文件

日期：2026-10-27。状态：可供实现的第一版方案；已完成概念渲染，尚未实现网站或验证用户效果。

上位产品规划见 [整体 PRD](PRD.md)。本文件负责第一版实现细节；产品目标、需求优先级和长期演进以 PRD 与最新用户决策为准。

## 1. 产品边界与成功条件

目标：通过一次旅行复盘建立经本人确认的偏好，帮助旅行者逐步完成下一趟旅行的准备、选择与可修改行程。

首个重点验证目的地为伦敦。选择依据是项目发起人具有较丰富的伦敦旅行经验，能够提供真实经历并判断推荐是否符合偏好、路线是否合理、安排是否值得。该选择用于集中内容核验与测试投入，不是对用户身份的硬性准入限制。

出发地、护照、居住地、职业、人数、预算和天数均为可变输入；“北京出发、1—2 人、5—8 天”等仅可作为某条测试样例，不作为网站固定条件。首版优先把伦敦市内规划闭环做完整，其他目的地标记尚未系统验证，不把保存草稿等同于已具备可靠规划能力。

行程规划与签证覆盖分开管理：旅行者可先复盘、比较候选或规划伦敦活动，不必先完成签证问卷。签证模块被启用时，按护照、合法居住地、旅行目的和已有入境许可确认适用路径；优先核验英国旅游访客场景，未覆盖的条件明确说明，不能仅因目的地为伦敦就套用同一份材料清单。英国签证内容独立建立，不沿用法国/申根模板。

伦敦验证样例覆盖：已有入境许可只需规划、需要准备访客申请、独行/双人、短住/较长停留、摄影优先/口味优先、预算变化与已订项目锁定。可先用明确标记的合成输入验证交互，再引入本人真实经历检验匹配；发起人经验属于重要评审证据，不能代替实时营业/预约核查或其他旅行者反馈。

核心闭环：可选复盘 → 确认偏好 → 确认本次条件 → 准备清单 → 比较方案 → 每日行程 → 局部修改 → 导出 → 轻量反馈。

第一版不包含付款、代办签证、自动预约、全平台实时比价、群体模型训练、跨设备同步、多人实时协作和证件原件识别。保留照片作为本地复盘素材；不根据照片自动判定人格。

## 2. 输入与输出契约

| 模块 | 输入 | 输出 | 确认与边界 |
|---|---|---|---|
| 旅行复盘 | 可选文字经历、预算及口径、酒店/餐厅/景点、满意与失望原因；可选 1—3 张照片及说明 | 结构化经历卡、3—5 条候选偏好 | 缺失不补造；照片默认仅本地展示；候选偏好须本人确认 |
| 偏好档案 | 候选偏好的接受/修改/拒绝、适用范围 | 长期偏好、情境偏好、单次约束 | 保存来源及状态；不将一次消费认定为长期消费能力 |
| 旅行条件 | 目的地、日期或弹性、人数、出发地、预算、是否含机票、旅行期待；签证所需身份条件按需询问 | TripBrief；已知/暂定/缺失条件 | 每轮最多 1—2 个影响当前决定的问题，允许跳过 |
| 出行准备 | TripBrief、护照签发国、居住情况、旅行目的、已核验规则模板 | Milestone、Task、官方入口与核查时间 | 建议日期和官方要求分开；未验证适用性时不输出确定结论 |
| 住宿与交通 | 已确认偏好、预算、区域选择；可选旅客录入的航班/酒店与报价 | 每轮 2—3 个候选、匹配理由、取舍、费用口径、来源及跳转 | 无接口时采用搜索跳转与人工录入；无报价时显示未知 |
| 每日行程 | 选定候选、时间约束、预约信息 | 按日期与早/午/晚组织的条目、交通、预约状态 | 显示估算/已核实；时间不足或冲突时要求取舍 |
| 对话修改 | 目标条目 ID、修改请求、当前计划版本 | 变更预览、冲突、预算影响、应用/撤销 | 锁定条目不可被静默修改；修改与版本检查原子提交 |
| 总览 | 当前已确认计划 | 手绘风格摘要、打印/PDF、JSON 备份 | 不包含未确认敏感信息；未知字段保留未知；摘要与计划同源 |
| 反馈 | 接受/替换理由、旅行后期望与实际差异 | 本地反馈记录、待确认偏好调整 | 不自动上传进行群体训练 |

价格结构至少包含金额、币种、人均/总额、晚数/人数、含税/行李情况、来源、查询时间、estimate/quoted/user-entered 状态。未知项不得默认为 0。

## 3. 信息架构和页面

首页：一段简短说明、两个入口“开始规划”“复盘一次旅行”，允许直接恢复草稿。不放功能墙、复杂图表或长表单。

工作台导航分为五栏，分别是独立路由或可恢复状态的视图：

1. 旅行偏好：复盘、偏好确认和编辑。一次只确认一组信息。
2. 出行准备：里程碑列表，默认只展开当前里程碑；详情包含 checklist 和来源。
3. 住宿与交通：住宿区域/酒店/交通分步骤，默认只展示当前步骤的 2 个候选，最多 3 个。
4. 每日行程：日期切换，默认只展示当天；地图为可切换视图，不与全程时间轴同时铺满屏幕。
5. 旅行总览：简洁全程摘要和导出；手绘插画辅助表达，不承担准确导航。

偏好和数据设置入口固定可达，支持导出、导入、清除及降低透明度。切换栏保留未提交输入；不强制按向导顺序锁死导航，缺少前置条件时说明原因并提供返回入口。

## 4. 核心布局

桌面宽度 ≥1280px：顶部 64px；左导航 176—192px；主工作区在剩余区域居中，建议最大 1040px。外边距 24px，栏间距 24—32px。取消默认右侧常驻对话栏，改为主工作区底部居中的玻璃对话舱，宽度 560—720px、不超过可用宽度减 32px。收起时只显示输入框、当前上下文和展开按钮；展开时向上出现最近对话与待确认建议，最大高度 40vh。内容区预留底部空间，焦点元素不可被遮挡。

768—1279px：左导航收为窄栏或抽屉；对话舱固定底部，展开为底部面板。避免三栏挤压正文。

<768px：单列内容；底部简洁对话入口，展开为近全屏对话页，关闭后恢复计划滚动位置。阶段导航进入抽屉或顶部选择器。候选卡纵向排列；不要求横向滚动。输入框避开软键盘及安全区。不支持自由拖动。

桌面可选浮动模式：通过专用拖动手柄移动对话舱，可吸附到底部、左侧或右侧；支持一键复位和位置菜单，键盘也能选择停靠位置。位置保存在本设备，窗口缩小时自动约束在可视范围。拖动不触发发送或选择文字。首版仅保留有限尺寸，避免复杂的任意缩放。默认底部停靠为稳定体验，自由浮动为个性化选项。

单屏原则：一个主要问题、一个主要行动、最多三个候选。不并排展示签证全清单、预算大表、全程地图及所有聊天。信息不足以一屏展示时允许自然滚动，不缩小字号硬塞。

## 5. 视觉风格：液态玻璃 × 极简科技 × 手绘点缀

参考图：[桌面工作台概念渲染](design/travel-workspace-liquid-glass-v1.png)。由内置 image_gen 生成，属于视觉方向而非已实现页面。2026-10-27 根据反馈更新：该图的右侧常驻聊天布局已被底部对话舱方案取代，巴黎场景也已被伦敦优先验证方案取代；配色与材质仍作为参考，尚未生成新版渲染图。图中的照片是生成的概念素材，地点描述未经事实核验，不可作为真实旅行推荐直接上线。后续样例使用伦敦内容、英镑费用和 Europe/London 时区；实际费用仍保存原币种，时区需处理夏令时。

总体气质：珍珠白、冰蓝、少量淡紫环境光，深海军蓝正文、钴蓝主行动。科技感来自精确对齐、清晰层级和透明材质，避免霓虹、过量光晕、全屏动态粒子。

| text-primary | #12213A | 正文与标题 |

字体：系统中文无衬线，正文 16px、行高 1.6；辅助文字 14px；桌面主标题 32—40px，移动端 26—30px。字号随屏幕合理收敛，不依靠超大标题挤压内容。

玻璃层采用 backdrop-filter blur(18—24px)、细白色边缘与低强度阴影；正文底层接近不透明。关键交互边界不可只靠白色边线辨认。第一版使用 CSS 近似材质，不实现昂贵的实时光学折射。

手绘使用少量地标线稿、路线弧线、强调圈，工作台中面积约 3—5%；总览可略多。文字与真实路线由代码生成，手绘插画不改变地理或预约事实。装饰标记 aria-hidden，不代替按钮和状态提示。

渲染图落地修正：保存状态使用设备/硬盘图标，不能用云朵暗示云同步；街区“安静”等推测改为有来源、有条件的说明；候选照片采用有使用许可且与真实地点一致的素材。

动效：交互反馈 160—240ms，局部淡入与轻微位移，不做持续漂浮、长时间弹簧动画。尊重 prefers-reduced-motion；提供降低透明度设置及不支持 backdrop-filter 时的不透明回退。

## 6. 交互和状态规范

- AI 先提出结构化建议，旅行者确认后写入长期偏好或已选计划。普通解释不触发数据修改。
- 每个候选可展开“为什么适合”“取舍”“来源”；主卡保留简短摘要。
- 当选择已经确认，显示明确状态；锁定、暂定、已预约不得仅依靠颜色区别。
- 生成中显示真实阶段：理解条件、检索信息、整理候选；允许取消。不显示虚构进度百分比。
- 搜索失败保留现有计划并说明哪些信息未查到；提供重试及官方/平台入口，不用模型虚构结果补位。
- 网络中断时已保存内容仍可查看；暂停 AI 与实时检索；显示离线标识。
- 所有输入支持键盘、可见焦点和有意义的标签；抽屉关闭后焦点返回触发元素。
- 导入先预览并验证版本与结构；选择新建或替换；清除数据须明确确认；敏感内容不默认进入导出。
- 外部内容按不可信数据处理；清理 HTML 和链接协议；模型无法直接付款、预约或执行任意网页指令。

## 7. 数据模型与服务边界

建议基础实体：LocalProfile、Experience、Preference、Trip、Milestone、Task、Candidate、ItineraryItem、Source、PlanRevision、Feedback。

Preference 包含 id、dimension、value、scope(long-term/context/trip)、context、evidenceIds、status(proposed/confirmed/rejected)、updatedAt。推测可信度用文字状态；不生成未经校准的百分比。

Trip 包含 dateRange、timezone、travellers、budget、constraints、assumptions、version。ItineraryItem 使用稳定 ID、日期/时间、地点、cost、sourceIds、reservationStatus、locked；跨时区交通分别保存起止地时区。

Source 包含 url、publisher、retrievedAt、claim、verificationStatus；没有核查时间的内容不能标记“最新”。Feedback 区分推荐未选择、未体验、体验不满，不能一律写成 dislike。

计划修改使用 revision：模型返回 proposedPatch 与 baseVersion；客户端验证目标、锁定、字段、时间及预算后呈现 diff；确认后生成新版本，撤销恢复前一版本。旧版本回复不能覆盖更新后的计划。

推荐实现：React + TypeScript + Vite；CSS token + 原生可访问控件；Dexie/IndexedDB 存本地数据；Rough.js + SVG 生成手绘总览；服务端提供受控模型与检索代理。第一版不要求整套 fork 现有旅行系统。

建议接口：POST /api/experience/extract、/api/trips/clarify、/api/recommendations、/api/itinerary/propose-patch；响应必须通过结构校验。签证核验模板单独版本化发布，模型不得直接修改其事实字段。

## 8. 隐私与联网

偏好、经历、草稿、照片默认本地保存。浏览器清理和存储驱逐可能造成丢失，保存入口旁提供备份提示与 JSON 导出。

调用云端 AI 前说明将发送哪些字段，允许关闭经历参与；照片首版不发给模型。模型服务的数据留存政策必须核实后说明，不能承诺第三方零留存。应用日志不记录原始经历、照片和个人材料；服务端密钥不得打包进前端。

不上传护照和银行流水原件，不默认启用跨用户训练或行为追踪。未来群体推荐另设明确自愿的数据贡献入口，与本人规划授权分离。

内容检索优先官方签证/场馆来源。酒店与机票首版采用带查询条件的跳转和用户报价录入；不预设抓取平台可长期稳定工作。来源、预算估算和未验证字段应在导出中保持可辨识。

## 9. 实施阶段及交付

M0 视觉基线：旧版概念图、本文件、生成提示词已完成；新版伦敦＋底部对话舱渲染待完成。尚无运行网站。

M1 可交互骨架：五栏路由、响应式布局、设计 token、全部空/加载/错误状态、合成演示数据和离线草稿。演示数据须明确标注。验收：完整流程可点通，刷新可恢复，不存在假装成功的按钮。

M2 偏好闭环：复盘提取、本人确认、本地存储、编辑删除、导出恢复、云端处理说明。验收：一次临时取舍不会自动成为长期偏好。

M3 旅行规划：建立并核验英国旅游访客准备模板、伦敦来源卡、区域及候选比较、搜索跳转、日程草稿。模板当前尚未完成；以 GOV.UK 官方入口为依据。验收：不同签证条件分支分开处理；已有适用入境许可者可以跳过申请准备；每个事实性推荐有来源或明确标记待核实；未知报价不冒充实时价格。

M4 修改与交付：局部 patch、锁定、冲突提示、撤销、总览与打印导出。验收：自然语言修改只作用于目标范围，旧响应不能覆盖新版本。

M5 小范围试用：邀请 8—12 位有近期旅行意向者，观察能否独立完成偏好确认、识别下一任务、改变一天计划并再次回访。属于探索性验证，不能据此宣布推荐算法有效或市场验证成功。

## 10. 发布前检查

- 390px、768px、1280px、1440px 宽度与 200% 缩放：无横向溢出、内容遮挡或不可达操作。
- 正文对比度至少 4.5:1，大字至少 3:1；关键控件与状态图形满足适用的非文本对比要求。透明效果在实际合成背景上测试。
- 产品触控目标尽量 ≥44×44px；键盘完成导航、选择、对话、抽屉与导出；屏幕阅读器可理解状态。
- 低性能设备无连续重绘的大面积滤镜；可关闭动效及透明度。
- 关键逻辑测试：预算单位/未知金额、材料条件分支、锁定条目、版本冲突、撤销、本地迁移和导入恢复。
- 端到端测试：复盘→确认偏好→创建旅行→选候选→修改→刷新→导出；另测检索失败和离线。
- 人工核查示例行程的营业、交通、预约与签证链接；自动测试通过不等于旅行信息正确。

## 11. 导出流程与规格

入口：旅行总览的“导出旅行包”。打开独立导出视图，先选用途，再选内容并预览，最后保存到设备；不直接导出整段聊天。所有格式从同一计划版本生成，显示导出日期、版本、暂定与已确认状态。后续修改不会自动更新已经下载的文件。

首版提供三种输出：

1. PDF 旅行手册（默认）：封面及全程概要、按天行程、地址/交通/预约状态、预算估算与已确认费用、可选出行 checklist、来源链接。使用实底高对比打印样式，保留少量手绘，不复制网页的透明滤镜。优先实现专用打印页面与浏览器“保存为 PDF”；不能将此路径宣传为无需系统对话框的一键下载。地图如需联网需明确说明；文本在离线 PDF 中仍可读。
2. PNG 旅行分享卡：生成一张总览或逐日卡，不强制把所有细节挤成长图。默认只含日期、城市、主要活动和简化路线，不含精确住宿地址、确认码、个人资料和私人复盘。图片不是可编辑备份，也不承担准确导航。
3. JSON 可恢复备份：含 schemaVersion、计划、偏好、来源和修改所需稳定 ID；用户可选择是否包含私人复盘。首版默认不包含照片二进制和任何凭据，界面明确列出遗漏项。导入支持结构校验、版本迁移及新建副本，不能静默覆盖现有旅行。

导出前摘要显示将包含的字段、未完成任务、估算金额、需要联网的链接及被排除内容。个人旅行手册与分享卡使用不同隐私默认值。日期未定时允许导出并标记“暂定”；不把签证材料清单或规划手册描述为已获认可的签证递交材料。

导出实现：所有文字使用真实字体排版；印刷版用 CSS @media print/@page；图片版使用受控 SVG/Canvas 模板，注意第三方图片跨域、版权与字体加载，失败时退回无照片模板。渲染完成后再允许保存。JSON 本地生成，无需服务器存储。生成来源链接不能包含 token、会话参数或个人身份信息。

后续可增加 ICS 日历导出与自包含离线 HTML。ICS 需要处理时区与重复导入；离线 HTML 需要资源打包及外链边界。首版不提供公开分享链接，以免引入云端存储和公开访问权限问题。
