# 多模型开发与审查流程

日期：2026-10-27。状态：已确定分工方向，外部模型执行环境尚未核验；尚未向 Opus 或 DeepSeek 派发开发任务。

## 1. 分工原则

用户提出由 Claude Opus 5.5 搭建骨架，DeepSeek 完成边界清晰的实现，当前助手负责 review。此处指开发网站的协作流程，不是网站上线后的模型路由；运行时模型仍按 PRD 单独选型。

模型的品牌不作为质量担保。成本同时计算推理、上下文交接、返工和审查；通过一个相同的小任务试运行确认实际性价比。DeepSeek 的具体模型 ID、接入工具和费用上限在派发前核验，不静默指定或替换。

## 2. 角色与交付

| 角色 | 负责内容 | 必须交付 |
|---|---|---|
| Opus 5.5 | 工程骨架、架构边界、数据模型、接口契约、关键状态流、设计系统、一条纵向示范流程 | 可运行骨架、架构说明、schema、示范页面、关键约束测试、模块任务单 |
| DeepSeek | 在稳定契约内实现页面、卡片、清单、费用展示、导出模板及相应测试 | 小范围 diff、需求 ID、变更说明、运行命令与结果、未解决问题 |
| 当前助手 | 骨架审查、每批实现审查、集成与发布前检查 | 按严重程度排序的问题、复现步骤、测试及视觉证据、合入结论与剩余风险 |

Opus 的骨架不是空目录或只有说明的样板。至少应完成“创建旅行 → 本地保存 → 展示一个候选 → 修改并撤销”的可运行纵向切片，使用明确标记的合成数据。

高风险模块包括签证条件分支、本地数据迁移、授权边界、计划版本/锁定/撤销、外部模型代理与密钥。由 Opus 定义并示范不变量，DeepSeek 可以依据契约实现局部，但不得自行改动边界；当前助手必须审查关键逻辑与失败路径。内容事实仍需官方来源核验，不由任何模型自行背书。

## 3. 开发顺序与关口

1. 当前助手将 PRD 和实施文件整理为首个骨架任务包，明确伦敦、底部可移动对话舱、本地优先与三类导出。
2. Opus 实现骨架和纵向切片，提交接口、数据模型及测试证据。
3. 当前助手进行第一次 review；修复重大边界问题后冻结契约 v0.1，再分配批次。
4. DeepSeek 每批完成一条可验证的小功能，先自检再交付。不等待所有功能写完才 review。
5. 当前助手逐批验证需求、代码、测试及实际页面；问题回到对应实现角色修复，重大架构问题回到 Opus。修复后再检查。
6. 最终执行伦敦完整旅程、离线、版本冲突、导出恢复、响应式与隐私验收。

不允许多个角色同时修改同一组文件。优先采用独立分支/隔离工作目录与可审查提交；公共 schema、依赖版本和数据库迁移由明确的单一负责人协调。未经 review 的修改不合入发布版本。

## 4. 第一批任务拆分

| 批次 | 主实现角色 | 内容 | 依赖 |
|---|---|---|---|
| B0 | Opus | 架构、schema、UI token、路由、本地仓库接口、版本机制和纵向切片 | PRD |
| B1 | DeepSeek | 五分区外壳、底部对话舱、停靠与复位、空/错/加载状态 | B0 通过 review |
| B2 | DeepSeek | 经历卡、偏好确认/编辑、当地草稿与备份界面 | 稳定 schema 和存储契约 |
| B3 | DeepSeek | 候选比较、预算、日程呈现与局部修改界面 | 经过审查的约束/patch 服务 |
| B4 | DeepSeek | 准备清单界面、PDF/PNG/JSON 导出 | 已核验模板及导出契约 |
| B5 | 当前助手 | 集成审查、真实交互测试、质量与内容检查 | B1—B4 |

以上为任务边界，不是已经启动的代理分配；允许按 review 结果重排。

## 5. 通用任务包模板

每个任务包必须包含：

- 对应 PRD 的 Fxx/Axx 编号及目标；
- 基础提交/契约版本、允许编辑路径、依赖与禁止变更范围；
- 输入/输出 schema、成功与失败状态；
- 明确的验收场景与运行命令；
- 合成样例和必要上下文，不发送私人旅行经历、照片、密钥或生产数据；
- 交付格式：变更摘要、diff/提交、验证结果、已知限制。

如需改变 schema 或添加依赖，先形成具体变更提议与兼容性说明，经过内部审查再统一采用。不能为通过测试删除失败用例、降低约束或把错误伪装为成功。

## 6. Review 标准

- 需求：当前是伦敦验证且人群输入可变；不能回退为巴黎、固定北京人群或右侧常驻聊天。
- 正确性：未知金额、预算单位、日期/时区、锁定、重复请求、旧响应和撤销均有正确行为。
- 隐私：本地优先、处理授权、导出范围与实际网络请求一致；无凭据或私人原文进入日志。
- 体验：主内容居中，玻璃不损害阅读，浮动舱不遮挡，移动端与键盘可用。
- 内容：来源与时效明确；生成文案不能冒充核验事实；测试数据醒目标识。
- 工程：可运行、可恢复、有必要的测试，契约一致、依赖合理，不把重复实现当成模块隔离。

审查不仅评价代码文本，也运行相关测试与实际页面；自动测试通过不能代替视觉检查或签证事实核查。严重数据丢失、隐私泄漏、锁定破坏和错误签证分支未解决时，不通过发布审查。

## 7. 调用边界与接入条件

当前会话内置子代理模型列表不包含 Opus 或 DeepSeek，不能将普通子代理改名后声称已使用这两个模型。可使用用户已有的外部编码工具/经配置 API 在同一项目的隔离分支工作；也可由用户在相应工具执行任务包，再由当前助手读取结果 review。

正式派发前核验：模型标识、账号访问、执行工具、文件权限、费用上限、代码外发范围与真实运行结果。不默认跨模型传送凭据或个人资料，不自行更改全局模型配置。用户选择的模型不可在失败后静默替换。

官网可确认模型文档存在，不代表当前账号已经能调用：

- [Claude Opus 5.5 文档](https://platform.claude.com/docs/en/models/opus-5-5/overview)
- [DeepSeek 模型列表接口](https://api-docs.deepseek.com/api/list-models/)

## 8. 与运行时 AI 的区分

开发工具使用的 Opus/DeepSeek/Codex 不自动成为网站用户对话所使用的提供方。若未来网站也采用多模型分工，需要另外设计路由、预算、数据授权、超时降级与质量评测，并更新 PRD；本次分工不授权新增运行时外发数据。

## 9. 本机接入观察与推荐方式（2026-10-27）

只读检查发现：Claude Code 为 2.1.311，当前执行环境的 ANTHROPIC_BASE_URL 主机为 api.deepseek.com；ANTHROPIC_MODEL、ANTHROPIC_DEFAULT_OPUS_MODEL、ANTHROPIC_DEFAULT_SONNET_MODEL 均为 deepseek-flash[1m]，HAIKU 与 CLAUDE_CODE_SUBAGENT_MODEL 为 deepseek-flash。未输出凭据，也未进行付费模型调用。此观察仅描述当前继承环境，不代表所有终端窗口或启动器均如此。

因此不能通过当前配置下选择 opus 别名就认定运行真正的 Claude Opus。DeepSeek 官方兼容接口也存在 Claude 名称映射机制：[说明](https://api-docs.deepseek.com/guides/anthropic_api/)。必须核验实际提供方和模型响应。

优先方案：独立 Opus 进程和 DeepSeek 进程，各自使用受控的启动环境、认证与模型标识；通过任务文件、代码提交及 review 交接。不要在共享的全局配置里来回改 endpoint。真正 Opus 的账号与启动配置尚未核验。

可先使用交互式人工启动；之后由当前助手在活动会话内通过 claude -p 调度受限任务，收集退出状态、结构化结果和代码差异。程序化入口参考 [Claude Code 文档](https://code.claude.com/docs/en/headless)。自动运行前核验权限、预算、供应商与工作目录；不使用跳过所有权限的参数解决配置问题。

子代理表示独立上下文和职责，不保证不同模型或不同供应商。Claude Code Agent Teams 提供共享任务与代理间消息，官方当前仍标注实验性：[说明](https://code.claude.com/docs/en/agent-teams)。本项目初期无需引入跨供应商网关，优先通过隔离进程完成可验证交接。
